# WisperBot Flutter SDK API Contract

This document describes only the Flutter API implemented by this package and
the checked-in Laravel visitor API it calls. The source of truth is
`D:\Backend\wisperbot\app\Modules\Inbox\routes\widget.php` and
`ChatWidgetPublicController.php` at backend commit `3dfe430`.

The backend repository is read-only reference material for SDK development.

## Public Flutter entry points

```dart
final config = WisperBotConfig(widgetKey: 'YOUR_WIDGET_KEY');
await WisperBotChat.open(context, config: config);
```

Supported presentation styles are `WisperBotChatScreen`,
`WisperBotChatLauncher`, `WisperBotChatView`, `WisperBotChat.open(...)`, and a
headless `WisperBotChatController`.

The controller supports:

```dart
Future<void> initialize();
Future<void> refresh();
Future<WisperBotMessage> sendText(String text);
Future<WisperBotMessage> sendImage(WisperBotUpload upload, {String? caption});
Future<WisperBotMessage> sendAudio(WisperBotUpload upload, {String? caption});
Future<void> setTyping(bool isTyping);
Future<void> requestHumanAgent();
Future<void> submitPreChat(WisperBotPreChatData data);
Future<void> updateUser(WisperBotUser? user);
Future<void> resetSession();
Future<void> dispose();
```

Passing `null` to `updateUser` is the host-application logout operation. It
stops polling, sends typing `false` on a best-effort basis, deletes the active
identity-scoped visitor ID/token, clears in-memory messages, and returns the
controller to `idle`. A later `initialize()` creates a fresh anonymous session.

There is no visitor realtime, server capability, unread/read-receipt, push,
device-registration, backward-pagination, or identity-outcome API in the
current backend or SDK.

## Identity and session storage

`WisperBotUser` maps directly to the session payload:

| Dart | JSON |
|---|---|
| `name` | `name` |
| `email` | `email` |
| `avatarUrl` | `avatar` |
| `externalId` | `external_id` |
| `signature` | `user_hash` |

Signatures are HMAC-SHA256 values generated by the integrating company's
server with the widget identity secret. The secret must never enter a Flutter
application. The backend does not report whether a supplied signature was
accepted, so the SDK exposes no verified/rejected identity status.

The encrypted visitor token is the authority for one conversation. The default
store keeps the matching visitor ID and token together in secure storage under
a base-URL, widget-key, and identity-scoped namespace. A caller-supplied visitor
or conversation ID never authorizes history.

## Required pre-chat

The first session response includes `require_prechat` and `prechat_fields`.
When required values are missing, state enters `awaitingPreChat` and the
composer remains hidden. The built-in UI collects `name` and/or `email`.
Headless integrations call:

```dart
await controller.submitPreChat(
  const WisperBotPreChatData(
    name: 'Jane Doe',
    email: 'jane@example.com',
  ),
);
```

Submission repeats `POST /widget/v1/session` with the current visitor ID,
visitor token, and supplied fields. Only a `preChatCompleted` flag is stored;
the SDK does not persist the submitted name or email. An unknown required field
produces `WisperBotErrorCode.unsupported`.

## Backend HTTP contract

Base path:

```text
{apiBaseUrl}/widget/v1
```

All requests send `Accept: application/json`. Authenticated requests also send
`X-Widget-Token`. JSON requests send `Content-Type: application/json`.
GET and multipart requests do not set JSON content type. The SDK never sends
`X-WisperBot-SDK`, media metadata headers, `Origin`, or `Referer`.

### Start or restore session

```http
POST /widget/v1/session
Content-Type: application/json
```

```json
{
  "key": "WIDGET_KEY",
  "visitor_id": "OPTIONAL_STORED_UUID",
  "name": "Jane Doe",
  "email": "jane@example.com",
  "avatar": "https://example.com/jane.jpg",
  "external_id": "customer-123",
  "user_hash": "SERVER_GENERATED_HMAC"
}
```

Restoration sends the stored visitor ID and matching token header. The response
contains `visitor_id`, `token`, `config`, `online`, `messages`, and `handoff`.
The backend issues a new isolated visitor when the ID/token pair is invalid.

Rate limit: 30 requests per minute.

### Send text

```http
POST /widget/v1/messages
Content-Type: application/json
X-Widget-Token: TOKEN
```

```json
{"key":"WIDGET_KEY","message":"Hello"}
```

Text is trimmed locally and limited to 4,000 characters. The response contains
the saved `message` and current `handoff`. There is no client idempotency key.
Rate limit: 60 requests per minute.

### Send image or audio

```http
POST /widget/v1/messages
Content-Type: multipart/form-data; boundary=...
X-Widget-Token: TOKEN
```

Multipart fields:

- `key`: widget key
- `type`: `image` or `audio`
- `message`: caption; the SDK sends an empty field when no caption is supplied
  to match the browser widget's multipart request shape
- `attachment`: file bytes, original filename, and the upload's explicit MIME
  type (for example, `image/png`)

The backend accepts up to 10 MB. Images are JPG/JPEG, PNG, or WebP. Audio is
MP3, AAC, M4A, AMR, OGG/OGA, WAV, or WebM. Laravel performs the authoritative
file validation; the SDK first rejects empty/oversized files and filename/MIME
mismatches. Media `422` maps to `attachmentRejected`.

Native clients do not send fabricated browser `Origin` or `Referer` headers.
Production hosting must allow authenticated native multipart requests to this
route. An HTML `406` response from the edge/WAF maps to `edgeRejected` rather
than being presented as Laravel validation.

The production edge fix is a narrow LiteSpeed/ModSecurity rule-ID exclusion
for `POST /widget/v1/messages`; it is hosting configuration, not a Laravel code
change. Do not disable the WAF globally. After the exclusion, a tokenless
native multipart request must reach Laravel and return `401 application/json`
instead of `406 text/html`. A widget used by native clients must also have an
empty browser-domain allowlist until the backend provides a native domain
policy.

### Poll

```http
GET /widget/v1/messages?key=WIDGET_KEY&after=123
X-Widget-Token: TOKEN
```

The response contains `messages`, `online`, `handoff`, `agent_typing`, and an
optional website `command`. Messages are ordered by ascending global database
ID and limited to 100. The SDK immediately fetches another page after a full
batch, deduplicates by server ID, and advances its receive cursor only from
session/poll batches—never from send responses.

Foreground polling uses the configured visible/idle intervals, never overlaps,
pauses without listeners or in background, and resumes with immediate
reconciliation. Rate limit: 300 requests per minute.

### Visitor typing

```http
POST /widget/v1/typing
Content-Type: application/json
X-Widget-Token: TOKEN

{"key":"WIDGET_KEY","is_typing":true}
```

Rate limit: 60 requests per minute.

### Human handoff

```http
POST /widget/v1/handoff
Content-Type: application/json
X-Widget-Token: TOKEN

{"key":"WIDGET_KEY"}
```

The returned handoff state is authoritative. The backend enables eligibility
after two visitor messages when an active AI chatbot is configured. Rate limit:
10 requests per minute.

## Message mapping

Backend messages contain `id`, `role`, `body`, `type`, `attachment_url`,
`filename`, `mime_type`, `sent_by`, `agent_name`, and `created_at`.

- Roles: `visitor`, `agent`, or safe `unknown`.
- Types: `text`, `image`, `audio`, `file`, or safe `unknown`.
- Agent sender kinds: `human`, `bot`, `automation`, `broadcast`, or `unknown`.
- Visitor messages normalize sender kind to `visitor`.
- Unknown additional JSON fields are ignored.
- Missing or malformed required fields produce a typed server error; the SDK
  does not invent timestamps or authoritative states.

## Errors and delivery

| HTTP | SDK result |
|---:|---|
| 400 | configuration |
| 401 | session expired; one controlled read recovery |
| 403 | forbidden domain/application |
| 404 on session | missing/disabled widget configuration |
| 404 authenticated | expired/unavailable conversation, then one recovery |
| 406 media | edge/WAF rejected native multipart upload |
| 413 | attachment too large |
| 422 media | attachment rejected |
| 422 other | validation |
| 429 | rate limited; honor `Retry-After` |
| 500–599 | server failure |

A media `422` preserves the backend's bounded attachment validation message
when present so the built-in composer can explain the rejection. Diagnostics
expose only HTTP status and a typed error code; they never include response
bodies, tokens, or media bytes.

In debug builds, the package also emits `logger` upload checkpoints for image
selection, byte size, MIME type, multipart construction, request dispatch,
HTTP status, and typed failure code. These logs intentionally omit filenames,
captions, tokens, URLs, and file contents, and are disabled in release builds.

A send becomes `sent` only when the server returns a message ID. Network or
server failure after transmission becomes `unconfirmed` because the backend may
already have stored the message. Unconfirmed sends are never retried
automatically or heuristically merged by body/timestamp.

## Security constraints

- Widget keys are public routing identifiers, not secrets.
- Visitor tokens are bearer credentials and are never logged.
- Identity secrets and management credentials never enter the package/example.
- Release builds require HTTPS.
- Native clients never spoof browser domain headers.
- Tokens, signatures, identities, message bodies, and attachment URLs are absent
  from diagnostics.
