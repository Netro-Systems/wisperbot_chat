# WisperBot Flutter SDK Agent Guide

This repository is the Flutter package `wisperbot_chat`. It provides a ready-made, customizable customer-chat experience backed by WisperBot's public widget API.

## Read first

Before changing code, read these files in order:

1. `PROJECT_GOAL.md`
2. `ARCHITECTURE.md`
3. `DESIGN_SYSTEM.md`
4. `API.md`

Update the relevant document whenever an implementation decision changes a documented public contract.

## Product definition

The SDK lets a Flutter developer add WisperBot chat with a widget key and a few lines of Dart. It owns session persistence, API communication, chat state, message delivery, and an optional prebuilt UI.

It must support five integration styles:

- Full-screen `WisperBotChatScreen`
- Floating `WisperBotChatLauncher`
- Embedded `WisperBotChatView`
- Modal or bottom sheet opened by `WisperBotChat.open(...)`
- Headless `WisperBotChatController` for fully custom interfaces

The SDK serves the customer/visitor side of chat. It is not the WisperBot agent inbox application.

## Package and platform strategy

- Start as a Flutter package, not a Flutter app or platform plugin.
- Prefer shared Dart and Flutter implementations on every platform.
- Target Android and iOS first while keeping the core compatible with Flutter Web and desktop.
- Add native Kotlin/Swift only when maintained Flutter packages cannot safely provide a capability such as attestation or specialized notification hooks.
- Keep platform code behind interfaces so the package can become federated later without breaking its Dart API.

Recommended creation command:

```bash
flutter create --template=package --platforms=android,ios,web,macos,windows,linux wisperbot_chat
```

## Non-negotiable engineering rules

- Never place the widget identity secret, workspace credentials, or management API credentials in the SDK or example app.
- `widgetKey` is a public routing identifier, not a secret.
- Verified identity signatures must be generated by the integrating company's server.
- Persist visitor tokens using secure storage, never plain `SharedPreferences`.
- Scope stored sessions by API base URL, widget key, and user identity so two users on one device never share history.
- Reset the active session when the host application's user changes or logs out.
- Never accept a caller-provided conversation ID as authorization. The encrypted visitor token is the authority.
- Do not log tokens, HMAC signatures, email addresses, message bodies, or attachment URLs in release builds.
- Stop polling when no listener needs updates or the app is backgrounded. Resume and reconcile when active.
- Deduplicate messages by server message ID.
- Preserve message order and prevent overlapping poll requests.
- Treat server configuration as the default and local theme overrides as presentation only.
- Do not force BLoC, Riverpod, Provider, or another host state-management package.
- Keep transport injectable and independently testable.

## Dependency policy

Keep runtime dependencies small and maintained. Hide dependencies that touch network, storage, lifecycle, media, or notifications behind interfaces.

Expected initial dependencies:

- `flutter`
- `http`, with an injectable `http.Client`
- `flutter_secure_storage`, behind `WisperBotSessionStore`
- `meta` only if it materially improves the API

Media picker, recorder, audio player, push, and deep-link dependencies belong in later milestones or optional adapters. Do not force heavy features into the core package.

## Architecture boundaries

Dependencies flow inward:

```text
UI -> controller/application -> domain <- data/transport/storage
```

- `domain` contains immutable models and repository contracts.
- `data` contains JSON mapping, HTTP, storage, and repository implementations.
- `application` coordinates session, polling, sending, lifecycle, and events.
- `ui` renders state and invokes the application layer.
- UI code must not call HTTP directly.
- JSON maps must not escape the data layer.
- Domain models must not depend on Flutter UI classes.

## Public API discipline

- Anything exported from `lib/wisperbot_chat.dart` is public and intentional.
- Keep implementation files under `lib/src/`.
- Prefer immutable public models with `const` constructors.
- Use enums or sealed types for known states and errors.
- Avoid public `dynamic` and untyped maps except documented metadata values.
- Adding a required constructor parameter is a breaking change.
- Mark experimental features clearly.
- Keep the API consistent across platforms. Report unavailable features through capabilities instead of silently behaving differently.

## State model

The controller exposes immutable state with these phases:

```text
idle -> initializing -> ready
                  \-> failure
ready -> reconnecting -> ready
ready -> expired -> initializing
ready -> disposed
```

State includes at minimum:

- Session phase
- Ordered messages
- Connection/polling status
- Online status
- Visitor and agent typing
- Handoff state
- Unread count when supported
- Pending sends/uploads
- Recoverable error

Do not represent expected UI states solely with exceptions.

## Error handling

- Convert failures into typed `WisperBotException` categories.
- Preserve HTTP status and safe server messages when useful.
- Mark errors retryable or non-retryable.
- Retry only safe operations automatically.
- Do not automatically retry sends until client message idempotency exists on the backend.
- A `401` visitor response triggers one controlled restoration attempt, never a loop.
- A disabled or missing widget is terminal until configuration changes.

## Testing requirements

Every behavior change needs proportionate tests. Minimum groups:

- JSON parsing and unknown fields
- New anonymous session and valid restoration
- Expired-token recovery
- Identity switching and logout reset
- Send/server-echo reconciliation
- Message deduplication and ordering
- Poll start, stop, pause, resume, and non-overlap
- Typing throttling and expiry
- Handoff eligibility and request
- Secure storage isolation
- Controller disposal and timer cleanup
- Full-screen, embedded, launcher, loading, empty, and error widget tests
- Accessibility semantics for composer, launcher, attachments, and unread badge

Use fakes instead of production requests in automated tests. The example may target explicitly selected staging.

## Quality checks

Before handing off a completed change, run:

```bash
dart format --output=none --set-exit-if-changed .
flutter analyze
flutter test
```

Run platform builds when changing platform configuration or dependencies.

## Documentation and examples

- Keep the README's first successful integration under ten lines where practical.
- Include anonymous and verified-user examples.
- Explain that signatures come from the customer's backend.
- Include full-screen, launcher, embedded, modal, and headless examples.
- Maintain a platform capability matrix.
- Never use real production credentials or personal data in examples.

## Definition of done

A change is done when:

- Behavior matches these specifications.
- Public API and migration implications are documented.
- Tests cover success, failure, and relevant lifecycle behavior.
- Formatting, analysis, and tests pass.
- No secrets or private user data are logged or committed.
- The example builds and demonstrates the affected feature.
